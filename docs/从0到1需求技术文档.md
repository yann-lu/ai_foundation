# AI Foundation 从 0 到 1 需求技术文档

> 本文档基于 ai-foundation 项目代码梳理，描述一个可配置的业务 AI Agent 平台的完整业务需求与技术实现要点，可作为从零开发的参考蓝图。

---

## 一、产品定位与目标

### 1.1 产品定位

AI Foundation 是面向企业业务系统的 **AI Agent 基础平台**，核心目标是把不同业务系统的 API、页面、知识库、提示词技能统一抽象为 Agent 可调用能力，通过聊天 SDK 和管理后台对外提供服务。

简单说：业务系统把自己的接口和页面注册进来，平台自动变成一个能对话、能查数据、能跳页面、能读文档的 AI 助手。

### 1.2 核心价值

| 价值 | 说明 |
|---|---|
| **统一能力接入** | 业务 API、页面跳转、知识库、提示词技能，全部统一接入 |
| **可配置、零代码** | 管理后台配置即生效，不需要发版 |
| **多租户隔离** | 按项目/产品/集团/酒店多级隔离 |
| **对话式交互** | 用户用自然语言就能操作业务系统 |
| **可扩展架构** | 新能力（工具/Skill/知识库）插件式接入 |

### 1.3 目标用户

- **终端用户**：业务系统用户（酒店员工等），通过嵌入到业务系统的聊天 Widget 使用
- **配置管理员**：通过管理后台配置项目、CLI、Skill、知识库
- **开发者**：通过 OpenAPI Schema 批量导入业务接口

### 2.3 核心请求链路

```

        ↓  HTTP + SSE

        ↓
  LoginInterceptor (SSO鉴权) → OauthAspect (用户信息注入)
        ↓
Mediator Service
        ↓
AgentOrchestrator (Run编排入口)
        ↓
ReactAgentRunner (ReAct Agent执行)
        ↓
  ┌────┴────┬────────┬──────────┐
  ↓         ↓        ↓          ↓
 CLI工具   Skill    知识库    平台工具
 (API/    (提示词   (RAG    (天气/节假日

  ↓         ↓        ↓          ↓

```

### 2.4 关键设计原则

1. **不使用物理外键**：所有关联通过业务字段维护，便于分库分表
2. **逻辑删除**：统一使用 `is_delete` 字段，MyBatis-Plus 自动处理
3. **配置态与运行态分离**：CLI/Skill/KB 是配置，Conversation/Run/Message 是运行态
4. **能力目录统一抽象**：API、页面跳转、Skill、知识库统一抽象为 Capability
5. **事件驱动 UI**：通过 SSE 推送实时状态，前端无需轮询

## 三、鉴权与多租户体系

### 3.1 租户模型

四级隔离体系：

```
项目 (project)        → 最大隔离单元，能力归属
  └─ 产品 (product)   → 同一项目下的不同产品线
      └─ 集团 (bloc)  → 租户级，数据隔离
          └─ 酒店 (hotel) → 最细粒度，业务数据归属
```

### 3.2 鉴权方式

**Token 鉴权**：

- 前端在请求头中携带 `accessToken`
- `LoginInterceptor` 作为 WebFilter 拦截请求
- 调用 SSO 服务校验 token 有效性
- 校验通过后，用户信息存入 `UserInfoThreadHolder` (ThreadLocal)

**OauthAspect 切面**：

- 在 Controller 方法执行前，从 ThreadLocal 取出用户信息
- **强制覆盖**请求中的 `blocCode`、`operator`、`operatorId`、`accessToken`、`clientIp`、`traceId`
- **酒店权限校验**：非 admin 用户传了 `hotelCode` 时，校验其是否在用户有权限的酒店列表内（通过 EHR 接口获取）

### 3.3 权限校验规则

| 角色 | 说明 | 酒店权限校验 |
|---|---|---|
| Admin | 系统管理员 | 不校验（可切换任意集团） |
| 普通用户 | 业务用户 | 必须在 EHR 返回的酒店权限列表内 |

> 前端传的 `hotelCode` 不被覆盖，只做权限校验。集团编码和用户信息以 SSO 为准。

### 3.4 免鉴权路径

- `/chat/simplestream` — 简化流式接口
- `/admin/*` — 管理后台接口（有独立鉴权机制）

## 五、会话管理模块

### 5.1 业务需求

用户与 AI 的每一次对话就是一个会话（Conversation）。会话需要：

- 保存会话基本信息（标题、所属项目/产品/集团/酒店、用户）
- 保存会话内所有消息
- 维护会话摘要（压缩长历史，节省 token）
- 支持创建、查询列表、清空、删除
- 支持按时间滚动查询消息和轮次

### 5.2 核心数据结构

**`agent_conversation_info`**

| 字段 | 说明 |
|---|---|
| `conversation_code` | 会话对外编码（前端用这个） |
| `project_id` | 所属项目 |
| `product_code` | 产品编码（冗余，便于查询） |
| `bloc_code` | 集团编码 |
| `hotel_code` | 酒店编码 |
| `user_id` | 用户ID |
| `title` | 会话标题 |
| `summary` | 会话滚动摘要 |
| `model_name` | 默认模型（可选） |

**`agent_message_info`**

| 字段 | 说明 |
|---|---|
| `conversation_id` | 所属会话 |
| `role` | 角色：user/assistant/system/tool |
| `content` | 消息内容 |
| `attachments` | 附件JSON数组 |
| `turn_number` | 对话轮次（user+assistant 为一轮） |
| `token_count` | 消耗token数 |
| `duration_ms` | 耗时（毫秒） |

### 5.3 会话摘要机制

- 当对话轮次超过阈值（如 10 轮）时，自动触发摘要生成
- 使用专门的摘要模型调用 LLM 把更早的历史压缩成一段摘要文本
- 摘要存入 `agent_conversation_info.summary`
- Prompt 组装时，摘要 + 最近 N 轮对话共同作为历史上下文
- 近 N 轮以完整对话为准，摘要用于理解更早的意图和指代

### 5.4 对外接口

| 接口 | 路径 | 说明 |
|---|---|---|
| 创建会话 | `POST /chat/create` | 必须传 productCode，hotelCode 可选 |
| 查询会话列表 | `POST /chat/list` | 按用户+项目分页查询 |
| 清空会话 | `POST /chat/clear` | 保留会话，删除消息 |
| 删除会话 | `POST /chat/delete` | 软删除 |
| 查询最近消息 | `POST /chat/messages/recent` | 查最近N条 |
| 滚动查询消息 | `POST /chat/messages/scroll` | 按时间向前/向后翻 |
| 查询最近轮次 | `POST /chat/messages/turns/recent` | 按轮次查 |
| 滚动查询轮次 | `POST /chat/messages/turns/scroll` | 按轮次翻 |

## 六、Agent Run 编排模块（核心）

### 6.1 业务需求

用户发一条消息 → AI 理解 → 可能调用工具 → 返回结果。这个完整过程就是一个 Run。

Run 需要：

- 异步执行（立即返回 runCode，前端通过 SSE 订阅进度）
- 支持 ReAct 模式（推理+行动循环）
- 支持多种工具调用（API、页面跳转、Skill、知识库、平台工具）
- 支持取消执行
- 记录执行状态、token 消耗、耗时
- 实时推送执行进度（思考、工具调用、结果）

### 6.2 Run 生命周期

```
CREATED (已创建)
    ↓
EXECUTING (执行中)
    ├─→ COMPLETED (已完成)
    ├─→ FAILED (失败)
    └─→ CANCELLED (已取消)
```

### 6.3 创建 Run 流程

```
POST /chat/runs/create
    ↓
1. 校验会话存在且用户有权限
2. 限流校验（全局+单用户+并发数）
3. 保存用户消息到 agent_message_info
4. 解析附件，构建附件上下文
5. 创建 agent_run，状态=CREATED，runType=REACT
6. 异步提交执行（本地线程池 或 MQ）
7. 立即返回 runCode
    ↓
前端通过 /chat/runs/events 订阅 SSE 事件流
```

### 6.4 ReAct 执行流程

**入口**：`AgentOrchestrator.startRun()` → `ReactAgentRunner.execute()`

```
┌──────────────────────────────────────────────────┐
│ 1. 构建执行上下文 AgentExecutionContext            │
│    (集团/酒店/用户/时间 等)                        │
├──────────────────────────────────────────────────┤
│ 2. 加载项目能力目录                               │
│    (CLI + Skill + 知识库 + 平台工具)              │
├──────────────────────────────────────────────────┤
│ 3. 能力检索（召回+重排）                           │
│    从全量目录中挑出与用户问题最相关的能力           │
│    （工具太多时需要减少给模型的工具规模）           │
├──────────────────────────────────────────────────┤
│ 4. 组装系统提示词                                 │
│    系统上下文 + 会话摘要 + Run进度 + ReAct规则    │
│    + Skill索引 + 能力要点 + 知识库规则 + 回复规范   │
├──────────────────────────────────────────────────┤
│ 5. 注册工具                                       │
│    平台工具 + CLI工具 + Skill工具 + 知识库工具     │
│    + 文件上传工具 + 酒店攻略工具 + lookup工具      │
├──────────────────────────────────────────────────┤
│ 6. 调用 ReAct Agent (Spring AI Alibaba)           │
│    推理 → 行动(调用工具) → 观察结果 → 再推理 ...    │
│    直到得出最终答案或达到最大步数                   │
├──────────────────────────────────────────────────┤
│ 7. 保存结果                                       │
│    保存assistant消息、更新Run状态、记录token消耗   │
├──────────────────────────────────────────────────┤
│ 8. 推送 RUN_COMPLETE 事件                          │
└──────────────────────────────────────────────────┘
```

### 6.5 ReAct 系统提示词结构

系统提示词是 Agent 行为的核心约束，按顺序拼接：

```
【系统上下文】                         ← 强制注入：集团/酒店/操作人/时间等
【会话意图摘要 · 更早轮次】            ← 更早的历史压缩（有则有）
【当前 Run 进度】                      ← Plan模式或步骤执行时（ReAct单步通常没有）

你是酒店助手，采用 ReAct（推理+行动）模式...   ← 角色设定
【安全红线】禁止披露工具列表...
【最高优先级 · 附件与工具】
【推理阶段 · 思考区输出】
【行动阶段 · 工具调用】
【可用 Skill 索引】
【各 Skill 能力要点与提示】
（如有知识库）【知识库使用规则】
【文件与产物规则】
【最终回复规范】

【近期对话历史 · 最近 N 条消息】       ← 最近对话作为system块注入
（附件运行时提示）                     ← 有附件时追加
```

### 6.6 ReAct 工具清单

| 工具类型 | 命名规则 | 来源 |
|---|---|---|
| 平台默认工具 | `weather_query`、`holiday_query` 等 | 平台内置 |
| CLI API工具 | `{prefix}_cli_api_{action}` | agent_cli_command (API类型) |
| CLI 页面工具 | `{prefix}_cli_navigate_{action}` | agent_cli_command (PAGE类型) |
| Skill 工具 | `skill_{skillCode}` | agent_skill_definition |
| 知识库工具 | `knowledge_{kbCode}` / `knowledge_search` | agent_knowledge_base |
| 文件上传工具 | `upload_generated_file` | 平台内置 |
| 酒店攻略工具 | `generate_hotel_guide` | 平台内置（命中hotel_guide skill时） |
| 查找工具 | `lookup_cli` | 逃生舱，目录太大时用于按名查找 |

### 6.7 SSE 事件流

通过 `POST /chat/runs/events` 订阅，返回 text/event-stream。

**主要事件类型**：

| 事件 | 说明 |
|---|---|
| `run.start` | Run 开始执行 |
| `run.executing` | Run 执行中 |
| `react.think` | ReAct 思考过程 |
| `tool.start` | 工具调用开始 |
| `tool.end` | 工具调用完成 |
| `tool.fail` | 工具调用失败 |
| `chat.token` | 回复 token 流式输出 |
| `artifact.generated` | 生成了产物卡片（文件/攻略等） |
| `innerLink` | 页面跳转指令 |
| `run.complete` | Run 完成 |
| `run.error` | Run 出错 |
| `run.cancel` | Run 被取消 |

### 6.8 取消与确认

- **取消**：`POST /chat/runs/cancel` — 设置取消标记，ReAct 在下一步推理前检查并终止
- **确认**：`POST /chat/runs/confirm` — Plan 模式下的步骤确认，当前 Plan 模式已下线，此接口返回"请重新发起对话"

### 6.9 限流机制

三层限流（基于 Redis 滑动窗口）：

1. **全局限流**：整个系统每秒最大 Run 数
2. **单用户限流**：每个用户每秒最大 Run 数
3. **并发限流**：同时执行中的最大 Run 数（占坑，完成后释放）

## 七、能力目录与工具系统

### 7.1 业务需求

平台的核心价值在于把各种业务能力统一抽象，让 Agent 能调用。能力分为四大类：

| 能力类型 | 说明 | 示例 |
|---|---|---|
| `API` | 调用业务系统 HTTP 接口 | 查询订单、获取酒店信息 |
| `NAVIGATE` | 跳转业务系统页面 | 打开订单详情页、弹新增框 |
| `SKILL` | 基于提示词的复合能力 | 营收分析、周边攻略生成 |
| `KNOWLEDGE` | 知识库检索问答 | 查询制度、操作手册 |

### 7.2 CLI 系统（API + NAVIGATE）

CLI 是 Agent 可调用命令的统一抽象，不管底层是 API 调用还是页面跳转。

**`agent_cli_command` 核心字段**：

| 字段 | 说明 |
|---|---|
| `command_prefix` | 命令前缀，如 `epms`、`pmsplus` |
| `command_group` | 命令分组，如 `order`、`hotel` |
| `command_action` | 命令动作，如 `query`、`getinfo` |
| `command_name` | 完整命令名 = prefix_cli_类型_action，如 `epms_cli_api_order_query` |
| `cli_template` | 人类可读的命令模板描述 |
| `description` | 命令说明（模型据此判断是否调用） |
| `command_type` | `API` 或 `PAGE` |

**参数定义**（`agent_cli_param`）：

- 支持 `flag` 标记（布尔型参数）
- 支持 `string`、`number`、`boolean`、`array`、`object` 类型
- 支持子字段（`parent_param_name` 表示嵌套，如 `filter.criteria`）
- 支持 `is_required`、`default_value`、`description`
- 有 `sort_order` 控制展示顺序

#### 7.2.1 API 型 CLI

底层关联 `agent_tool_definition`（HTTP 请求定义）：

| 字段 | 说明 |
|---|---|
| `url` | 请求 URL |
| `method` | HTTP 方法 |
| `auth_type` | 鉴权方式 |
| `request_schema` | 请求体 JSON Schema |
| `response_schema` | 响应体 JSON Schema |

**执行流程**：

```
模型调用 CLI 工具（传参数）
    ↓
CliParamBinder 绑定参数
  - 用户原始指令
  - 参数定义 + 默认值
  - 系统上下文（blocCode/hotelCode 等自动注入）
  - 历史对话和摘要
  - 前序步骤结果
    ↓
ApiToolExecutor 发起 HTTP 请求
  - header 自动注入：x-bloc-code、x-hotel-code、x-product-code、accessToken 等
    ↓
ApiToolResultInterpreter 用 LLM 解释/摘要结果
  - 把 API 返回转成自然语言摘要
  - 业务失败时生成友好回复
    ↓
返回给 Agent 继续推理
```

#### 7.2.2 PAGE 型 CLI

底层关联 `agent_page_definition`（页面跳转定义）：

| 字段 | 说明 |
|---|---|
| `page_route` | 路由路径 |
| `display_type` | `PAGE`（页面跳转）或 `MODAL`（弹窗） |
| `target_type` | `INTERNAL`（内部路由）或 `EXTERNAL`（外链） |
| `resource_project` / `resource_ids` | 资源权限校验 |

**执行流程**：

```
模型调用 NAVIGATE 工具
    ↓
ResourcePermissionValidator 校验页面资源权限
    ↓
CliParamBinder 绑定页面参数
    ↓
NavigateExecutor 生成跳转协议
    ↓
通过 SSE 推送 innerLink 事件给前端
    ↓
SDK 接收后跳转页面或弹框
```

**前端跳转协议**：

```json
{
  "title": "订单详情",
  "page": "/order/detail",
  "display": "PAGE",
  "target": "INTERNAL",
  "data": { "orderId": "12345" }
}
```

### 7.3 Skill 系统

Skill 是高阶复合能力，当前主要是 **PROMPT 类型**（基于 system_prompt 的提示词技能）。

**`agent_skill_definition` 核心字段**：

| 字段 | 说明 |
|---|---|
| `skill_code` | Skill 编码（唯一） |
| `skill_name` | Skill 名称 |
| `description` | 描述（模型据此判断是否使用） |
| `skill_type` | `PROMPT` / `WORKFLOW` / `MULTI_AGENT`（后两者预留） |
| `system_prompt` | 核心提示词 |
| `config_json` | 扩展配置 |

**Skill 资源绑定**（`agent_skill_resource`）：

- `resource_type`：`CLI` / `KB` / `MODEL` / `SKILL`（子 Skill）
- Skill 执行时会自动读取绑定的资源，注入到上下文中

#### Skill 执行流程（ReAct 模式）

```
模型调用 skill_{skillCode} 工具
    ↓
读取 Skill 定义 + 绑定资源
    ↓
组装 Skill system_prompt + 上下文
    ↓
调用 LLM 生成结果（PROMPT类型）
    ↓
后处理（如 hotel_guide 生成卡片）
    ↓
返回结果给 Agent 继续推理
```

#### Skill 与 CLI 的协同

Skill 的输出中可以包含指令，Agent 会根据指令自动执行后续 CLI：

- `【建议调用】工具=<commandName> 参数=key=value,... 说明=...` → 自动调用 API
- `【建议跳转】...` → 自动执行页面跳转

#### 特殊 Skill：酒店攻略 (`*_hotel_guide`)

内置处理器 `HotelGuideCapabilityHandler`：

- 识别规则：skillCode 以 `_hotel_guide` 结尾
- 提供专用行动规则（POI 搜索策略、酒店信息获取、攻略生成等）
- 生成结果后自动推送 `hotel_guide` 卡片产物
- 禁止使用 `upload_generated_file`（攻略以卡片交付）

### 7.4 能力目录与检索

**能力目录**（`CapabilityCatalog`）是项目维度所有可用能力的统一视图。

**缓存**：项目能力目录缓存在 Redis 中，管理后台修改后通过缓存刷新接口更新。

**能力检索**（`CapabilityRetriever`）：

当项目绑定的能力太多（超过阈值）时，不能全部塞进系统提示词，需要做检索：

1. **召回**：根据用户问题的语义/关键词，从全量目录中召回 Top N 个候选能力
2. **重排**：用 LLM 或重排模型对候选能力做精排，选出最相关的 M 个
3. 只把这 M 个能力注入系统提示词和注册为工具

> 召回标签（`agent_cli_recall_tag`）：为每个 CLI 配置召回标签，提升召回准确性。

### 7.5 OpenAPI 批量导入

管理后台支持通过 OpenAPI Schema 批量生成 CLI：

1. 配置 Schema（URL 或 classpath 资源）
2. 解析 Schema，提取所有接口
3. 自动生成 CLI 命令（command_name、参数、描述等）
4. 批量创建 `agent_cli_command` + `agent_tool_definition` + `agent_tool_param`

## 八、RAG 知识库模块

### 8.1 业务需求

企业内部有大量文档（制度、手册、FAQ、操作指南），需要让 AI 能够基于这些文档回答问题，避免编造。

功能需求：

- 管理知识库（增删改查）
- 上传文档（支持 PDF、DOCX、TXT、Markdown、Excel/CSV 等）
- 自动解析和切片
- 向量化存储到 Milvus
- 语义检索（按问题找出最相关的文档片段）
- Agent 可以调用知识库工具获取答案

### 8.2 数据模型

```
agent_knowledge_base (知识库)
  └─ agent_knowledge_document (文档)
      ├─ agent_knowledge_chunk (切片)
      └─ agent_knowledge_document_asset (衍生资源：图片/表格/扫描页)
```

**知识库**（`agent_knowledge_base`）：

| 字段 | 说明 |
|---|---|
| `kb_code` | 知识库编码 |
| `kb_name` | 知识库名称 |
| `biz_domain` | 业务域 |
| `embedding_model` | 向量化模型 |
| `chunk_strategy` | 切片策略 |
| `retrieval_config` | 检索配置（JSON） |
| `doc_count` / `chunk_count` | 文档/切片数量统计 |

**文档**（`agent_knowledge_document`）：

| 字段 | 说明 |
|---|---|
| `doc_name` | 文档名称 |
| `doc_type` | 文档类型（TEXT/TABLE/MIXED/SCAN） |
| `file_url` | 文件地址 |
| `parse_state` | 解析状态：待处理/解析中/已完成/失败 |
| `content_mode` | 内容形态（纯文本、表格、图文混合等） |

**切片**（`agent_knowledge_chunk`）：

| 字段 | 说明 |
|---|---|
| `chunk_index` | 切片序号 |
| `content_type` | 内容类型 |
| `content` | 切片文本内容 |
| `anchor_text` | 锚文本（标题等） |
| `token_size` | token 大小 |
| `page_no` / `sheet_name` / `row_start/end` | 来源定位 |
| `vector_id` | 向量库中的 ID |

### 8.3 文档入库流程

```
管理后台上传文档
    ↓
写入 agent_knowledge_document，parse_state=待处理
    ↓
异步解析任务
    ↓
1. 下载文件
2. 按文件类型提取文本
   - TXT/MD：直接读取
   - PDF/DOCX：提取文本 + 内嵌图片
   - Excel/CSV：转 Markdown 表格
3. 文本切片（按 token 大小 + 语义边界）
4. 生成 embedding（调用 bge-m3 等模型）
5. 写入 Milvus 向量库
6. 切片数据入库 agent_knowledge_chunk
7. 更新文档状态、知识库统计数
```

### 8.4 向量检索

```
用户问题
    ↓
生成 query embedding
    ↓
Milvus 向量相似度搜索（COSINE）
    ↓
Top K 结果（默认 5 条）
    ↓
过滤：分数阈值 > 0.12
    ↓
返回给 Agent / LLM
```

**配置要点**：

- Embedding 模型：`bge-m3`
- 向量维度：1024
- 距离度量：COSINE
- Milvus collection 前缀：`agent_kb_`
- 默认 TopK：5
- 最低分阈值：0.12

### 8.5 知识库路由

当项目绑定多个知识库时：

- Agent 可以用 `knowledge_{kbCode}` 工具检索指定知识库
- 也可以用 `knowledge_search` 工具自动选择最合适的知识库
- `KnowledgeKbRouter` 负责路由决策

### 8.6 Skill 与知识库结合

Skill 可以通过 `agent_skill_resource` 绑定知识库：

1. 执行 Skill 时，先用用户问题检索绑定的知识库
2. 把检索到的知识片段拼入 Skill 的 system_prompt
3. 模型基于知识片段回答问题，禁止编造

### 8.7 检索日志

每次检索都可以记录到 `agent_retrieval_log`，便于排查和优化：

- 原始 query、改写后的 query
- 选中的知识库、候选列表
- 召回片段快照、召回数量、重排数量
- 耗时、失败原因

## 九、系统提示词与上下文体系

### 9.1 上下文组成

每次 LLM 调用前，需要组装完整的 Prompt 上下文。上下文由多个块组成：

| 块 | 说明 | 来源 |
|---|---|---|
| 系统上下文 | 集团/酒店/操作人/时间等 | AgentExecutionContext |
| 会话摘要 | 更早历史的压缩 | agent_conversation_info.summary |
| Run 进度 | 已完成步骤结果 | AgentPromptContext |
| 业务系统提示词 | ReAct规则 / Skill提示等 | 动态组装 |
| 近期对话历史 | 最近 N 轮对话 | agent_message_info |
| 附件内容 | 用户上传的附件解析文本 | AttachmentContextService |
| 用户消息 | 当前用户输入 | 请求传入 |

### 9.2 系统上下文块（强制注入）

**格式**：

```
【系统上下文】
- 集团编码：BL001
- 酒店编码：HT12345
- 当前操作人：zhangsan
- 操作人 ID：10086
- 今日日期：2026-08-08
- 当前时间：14:30:00

请结合以上上下文理解用户诉求；涉及租户或权限时请以上下文为准。
调用 API/跳转工具时，若用户未指定酒店/集团/产品/操作人，直接使用上述上下文值，勿向用户追问。
```

**字段来源**：

| 字段 | 来源 | 是否被SSO覆盖 |
|---|---|---|
| `blocCode` | SSO Token 解析 | ✅ OauthAspect 强制覆盖 |
| `hotelCode` | 前端请求 → 回退会话存储值 | ❌ 前端传入，仅权限校验 |
| `operator` | SSO Token（userAccount） | ✅ 强制覆盖 |
| `operatorId` | SSO Token（userId） | ✅ 强制覆盖 |
| `currentDate` | 服务端 `LocalDateTime.now()` | 服务端生成 |
| `currentTime` | 服务端 `LocalDateTime.now()` | 服务端生成 |

**关键约束**：
> 调用 API/跳转工具时，若用户未指定酒店/集团/产品/操作人，直接使用上述上下文值，勿向用户追问。

### 9.3 上下文组装流程（ReAct 模式）

```
AgentExecutionContextBuilder.build()
    ↓ 生成 AgentExecutionContext

AgentContextPromptFormatter.format()
    ↓ 格式化为【系统上下文】文本

PromptHistoryProvider.buildSystemPrompt()
    ↓ 合并：系统上下文 + 会话摘要 + Run进度 + 业务prompt

+ 历史对话块（格式化为system文本）
+ 附件运行时提示
    ↓
最终 System Prompt → 注入 LLM
```

### 9.4 附件处理

用户上传附件后：

1. 文件保存到对象存储
2. 记录到 `agent_attachment_info`
3. 解析附件内容（文本提取）
4. 组装为附件上下文文本
5. 注入到当前轮 Prompt 的用户消息前（或单独的附件块）

ReAct 提示词中有专门的附件优先级规则：
- 附件正文是本轮主要数据来源
- 有匹配页面跳转时优先跳转
- 无跳转时基于附件作答，禁止重复调用 API 拉取已有数据
- 仅当需要附件以外的最新数据时才调业务 API

## 十四、核心技术点总结

### 14.1 AI Agent 技术

- **ReAct 模式**：基于 Spring AI Alibaba 的 ReactAgent，推理-行动-观察循环
- **动态工具注册**：每次 Run 根据能力检索结果动态注册工具
- **系统提示词工程**：多层块结构，精细控制 Agent 行为
- **多角色模型**：不同任务使用不同模型，平衡效果和成本

### 14.2 架构设计

- **分层架构**：com → dal → biz → mediator → gateway，职责清晰
- **能力抽象统一**：API、页面、Skill、知识库统一为 Capability
- **插件式扩展**：新能力、新工具可以独立添加
- **事件驱动 UI**：SSE 流式推送，用户体验好

### 14.3 工程化

- **MyBatis-Plus + 逻辑删除**：统一的数据访问模式
- **Redis 多层缓存与限流**：性能保障
- **全链路 Trace**：traceId 贯穿全链路，便于排查
- **Token 消耗统计**：成本可量化
- **异步化执行**：Run 异步执行，前端 SSE 订阅

### 14.4 RAG 技术

- **向量检索**：Milvus + bge-m3，1024 维，COSINE 相似度
- **多模态文档解析**：文本、表格、图片、扫描件
- **切片策略**：token 控制 + 语义边界
- **知识库路由**：多知识库自动选择
