## 核心概念

CLI（Command Line Interface）能力是 Agent 可以调用的**工具**。每个 CLI 命令代表一个可执行的操作，可以是调用一个 API 接口（API 型），也可以是跳转到一个页面（PAGE 型）。

大模型不是通过"解析命令名"来理解工具的，而是通过**功能描述 + 参数 JSON Schema** 来理解。命令名只是一个全局唯一的工具 ID。

```
大模型判断逻辑：
用户提问 → 扫描所有工具的 description → 选最匹配的 → 按 parameters 填参 → 调用
```

## 三级命名体系：前缀 / 分组 / 动作

### 是什么

所有 CLI 命令按「前缀 → 分组 → 动作」三级组织：

| 层级 | 字段 | 说明 | 示例 |
|---|---|---|---|
| 前缀 | `commandPrefix` | 哪个业务系统 / 产品 | `epms`、`pms`、`crs` |
| 分组 | `commandGroup` | 系统下的业务模块 | `order`、`room`、`finance` |
| 动作 | `commandAction` | 具体的操作 | `list`、`get`、`create`、`cancel` |

### 为什么要三级结构

1. **避免命名冲突** — 不同系统下都可以有 `order list`，前缀区分开就不重名了
2. **方便管理** — "给我看 EPMS 下所有订单相关的命令"，按前缀+分组筛选即可
3. **辅助召回** — 向量检索和标签匹配时，前缀/分组信息可以作为额外的召回信号
4. **人类可读** — 看到命令名就知道属于哪个系统、哪个模块、做什么操作

### 命名建议

- 前缀：用产品/系统的英文缩写，全小写，如 `epms`、`pms`、`crs`、`crm`
- 分组：用业务域的英文单词，全小写，如 `order`、`room`、`guest`、`invoice`
- 动作：用动词或动词短语，全小写，推荐用标准 CRUD 风格：
  - 查询列表 → `list`
  - 查询单条 → `get` / `detail`
  - 创建 → `create` / `add`
  - 更新 → `update` / `modify`
  - 删除 → `delete` / `remove` / `cancel`
  - 状态变更 → `setStatus` / `changeState`

## 命令标识 (commandName)

### 是什么

命令的全局唯一标识符，也是大模型调用工具时的 **tool name**。

命名规则：
```
{前缀}_cli_{类型}_{分组}_{动作}
```

示例：
- `epms_cli_api_order_list` — EPMS 系统的订单列表查询（API 型）
- `pms_cli_page_room_detail` — PMS 系统的客房详情页（PAGE 型）
- `crs_cli_api_booking_create` — CRS 系统的创建预订（API 型）

### 干什么用

1. **数据库唯一键** — `uk_command_name` 唯一索引，保证不重复
2. **大模型的工具名** — ReAct 框架注册 function tool 时，`name` 字段就是这个值
3. **代码和配置里的引用 key** — 缓存、向量索引、能力目录都用它做标识

### 大模型怎么理解它

**大模型不会去"拆"命令名来理解含义**。它主要看 `description`（功能描述）和 `parameters`（参数定义）。

命令名里的语义信息（`order`、`list` 等）只是辅助——大模型看到名字能大概猜是干嘛的，但真正决定调用的是功能描述。

> 💡 你可以把命令名想象成电话号码——你不会靠数字来记住一个人，但你拨电话时需要用它。

## 命令模板 (cliTemplate)

### 是什么

命令的"使用说明书"，以类 Shell 命令的格式展示给大模型看。

示例：
```
epms cli api order list <hotelCode>(required) <pageNo> <pageSize> <status>
```

- `<参数名>` 表示参数占位符
- `(required)` 表示该参数必填

### 和"CLI 命令预览"的区别

界面上看到的"CLI 命令预览"和数据库里存的 `cliTemplate`（命令模板）内容默认一致，但用途不同：

| 项目 | CLI 命令预览 | 命令模板 (cliTemplate) |
|---|---|---|
| 给谁看 | 后台管理员 | 大模型 |
| 可编辑 | 自动生成，实时预览 | 可以通过"高级编辑"手动修改 |
| 存储 | 不存，前端计算 | 存 `agent_cli_command.cli_template` |

### 为什么需要命令模板

1. **大模型的参考格式** — 大模型看到模板就知道参数顺序、哪些必填，更容易生成正确的调用
2. **调试和可读性** — 人类看命令结构也一目了然
3. **部分 Agent 框架用模板生成 prompt** — 有些编排方式会把模板作为 system prompt 的一部分注入

### 配置建议

- 默认自动生成的就够用了，不用手动改
- 如果有特殊的调用格式（比如参数有固定顺序、位置参数等），可以手动编辑模板来精确控制
- 必填参数一定要标 `(required)`，这是给大模型的强提示

## 功能描述 (description)

### 是什么

用自然语言描述这个 CLI 命令是干嘛的。**这是影响大模型调用准确率最重要的字段**。

### 为什么它最重要

大模型在几十上百个工具里选择"该调用哪个"时，主要靠**语义匹配描述文本**。描述写得越清楚，大模型越能准确判断：
- ✅ 什么时候该调用这个工具
- ❌ 什么时候不该调用
- 调用后能拿到什么结果

### 怎么写好功能描述

**不好的描述**（信息太少）：
```
查询订单
```

**好的描述**（场景 + 输入 + 输出都讲清楚）：
```
查询酒店订单列表，支持按酒店、日期范围、订单状态筛选。
返回订单号、房型、价格、入住人、入住离店日期等信息。
适用于用户问"某某酒店最近有哪些订单"、"查一下 BJ001 的在住订单"等场景。
必须传入 hotelCode（酒店编码）。
```

**写描述的黄金法则：**
1. ✅ 说清楚"做什么"——核心功能一句话讲明白
2. ✅ 说清楚"返回什么"——大模型需要知道调用后能拿到什么数据
3. ✅ 说清楚"适用场景"——举几个用户可能的问法（特别是别名/口语化说法）
4. ✅ 说清楚"必要条件"——比如必须有酒店编码
5. ❌ 不要写得太简短（比如只有 4 个字）
6. ❌ 不要写得太技术化（大模型理解业务描述比理解技术术语好）

## 命令参数 (agent_cli_param)

### 是什么

定义调用这个 CLI 命令需要传哪些参数，每个参数的类型、是否必填、默认值、描述等。

### 字段说明

| 字段 | 说明 | 示例 |
|---|---|---|
| `paramName` | 参数变量名，驼峰命名 | `hotelCode`、`pageNo` |
| `paramFlag` | 命令行标志（可选） | `--hotelCode` |
| `paramType` | 参数类型 | String / Number / Boolean / Array / Object |
| `itemType` | Array 元素的类型（仅 Array 时有效） | String |
| `isRequired` | 是否必填：0-否，1-是 | 1 |
| `defaultValue` | 默认值（可选） | 1、20 |
| `description` | 参数的描述（很重要！） | "酒店编码，如 BJ001" |
| `sortOrder` | 参数排序 | 0, 1, 2... |
| `parentParamName` | 父参数名（嵌套 Object 时用） | |

### 参数描述有多重要

**非常重要。** 大模型生成调用参数时，完全靠参数描述来理解每个参数该填什么。

**不好的参数描述：**
```
参数名: status
描述: 状态
```
大模型可能不知道填什么格式——是数字还是字符串？有哪些取值？

**好的参数描述：**
```
参数名: status
类型: String
描述: 订单状态，取值：CONFIRMED-已确认，CANCELLED-已取消，CHECKED_IN-已入住，CHECKED_OUT-已退房
```
大模型一看就知道传什么值。

### 参数配置最佳实践

1. **必填参数尽量少** — 越少，大模型越容易成功调用；能有默认值的就给默认值
2. **描述要写清楚取值范围/枚举值/格式** — 特别是状态、类型这种有固定选项的
3. **参数顺序按重要性排** — 最核心的参数放前面
4. **命名用驼峰，和后端接口字段一致** — 减少映射成本
5. **复杂嵌套用 Object 类型** — 但要谨慎，嵌套越深大模型越容易出错

## API 实现配置 (agent_tool_definition)

### 是什么

API 型 CLI 的底层接口配置，告诉系统调用哪个接口、怎么鉴权、请求和响应长什么样。

### 字段说明

| 字段 | 说明 | 示例 |
|---|---|---|
| `toolName` | 工具名称 | `epms-order-list` |
| `description` | 工具级别的描述（可选） | EPMS 订单列表查询 |
| `url` | 接口地址 | `/api/v1/order/list` |
| `method` | 请求方法 | GET / POST / PUT / DELETE |
| `authType` | 鉴权方式 | NONE / HEADER |
| `schemaCode` | 关联的 Schema 编码（可选） | |
| `requestSchema` | 请求 JSON Schema | 完整的 JSON Schema 定义 |
| `responseSchema` | 响应 JSON Schema | 完整的 JSON Schema 定义 |

### JSON Schema 的作用

**请求 Schema（requestSchema）**：
- 定义请求体的结构、类型、必填字段、枚举值、默认值
- 大模型用它来生成正确的入参
- 后端调用前也可以用它做参数校验

**响应 Schema（responseSchema）**：
- 定义返回值的结构
- 大模型用它来理解"调用后能拿到什么数据"
- 帮助大模型从返回结果里提取需要的信息

### Schema 配置建议

1. **必填字段一定要在 `required` 数组里列出来**
2. **有枚举值的一定要写 `enum`** — 比如状态、类型
3. **每个字段都要有 `description`** — 大模型靠描述理解字段含义
4. **嵌套不要太深** — 2-3 层以内最合适，太深大模型容易搞错
5. **示例：**
```json
{
  "type": "object",
  "required": ["hotelCode"],
  "properties": {
    "hotelCode": {
      "type": "string",
      "description": "酒店编码，如 BJ001"
    },
    "status": {
      "type": "string",
      "enum": ["CONFIRMED", "CANCELLED", "CHECKED_IN", "CHECKED_OUT"],
      "description": "订单状态"
    },
    "pageNo": {
      "type": "number",
      "default": 1,
      "description": "页码，从1开始"
    }
  }
}
```

## 召回标签 (agent_cli_recall_tag)

### 是什么

帮助系统更准确地把用户问题匹配到正确 CLI 命令的"标签"。相当于给每个 CLI 命令打一堆关键词标签，召回时加权匹配。

### 四种标签类型

| 标签类型 | 含义 | 示例 | 说明 |
|---|---|---|---|
| **ALIAS** | 用户说法别名 | "查订单"、"订单列表"、"看一下订单" | 用户可能会说的各种口语化说法 |
| **OP** | 操作码 | `list`、`get`、`create`、`cancel` | 动作/操作动词 |
| **DOMAIN** | 业务域 | `order`、`room`、`finance` | 所属业务领域，权重通常最高 |
| **SLOT** | 分槽 / 参数槽位 | `hotel_code`、`order_no` | 用户问题中包含的关键实体类型 |

### 字段说明

| 字段 | 说明 |
|---|---|
| `tagType` | 标签类型：ALIAS / OP / DOMAIN / SLOT |
| `tagValue` | 标签值 |
| `weight` | 权重（0-100），命中时加多少分 |
| `matchMode` | 匹配模式：exact（精确匹配）/ contains（包含匹配） |
| `sortOrder` | 排序 |

### 为什么需要召回标签

当 CLI 命令很多（几百上千个）时，不可能把所有工具都塞给大模型让它选（context 放不下，也浪费 token）。

所以需要**先召回再排序**的流程：
1. **召回阶段** — 用向量检索 + 标签匹配，快速从几百个工具里挑出 TopN 个最相关的
2. **排序/选择阶段** — 把 TopN 个工具的详细描述给大模型，让它选最终调用哪个

召回标签就是用来提高召回准确率的——特别是一些领域词、用户别名，光靠向量检索可能不够准。

### 配置建议

1. **DOMAIN 标签一定要加** — 业务域匹配是召回的核心锚点，权重设最高（10-20）
2. **ALIAS 标签多写几个** — 把用户可能说的各种说法都写上，用 contains 匹配模式，权重中等（3-5）
3. **OP 标签配标准动词** — list / get / create / update / delete 等，权重较低（2-3）
4. **SLOT 标签按需加** — 如果命令有明确的核心实体参数（如 hotelCode、orderNo），可以加
5. **不是越多越好** — 每个 CLI 5-10 个标签比较合适，太多反而会引入噪声

## 大模型调用工具的完整流程

```
用户提问
  │
  ▼
┌─────────────────────────────────────┐
│  1. 能力召回                         │
│  从全部 CLI 中选 TopN 个最相关的      │
│  方法：向量检索 + 标签匹配 + 关键词   │
└─────────────────────────────────────┘
  │  TopN CLI 列表
  ▼
┌─────────────────────────────────────┐
│  2. 工具注册                         │
│  把 TopN CLI 组装成 function tool    │
│  - name: commandName                 │
│  - description: description          │
│  - parameters: 参数 JSON Schema      │
└─────────────────────────────────────┘
  │  tools 数组（交给大模型）
  ▼
┌─────────────────────────────────────┐
│  3. 大模型选择工具并填参              │
│  大模型：                                                            │
│  - 扫一遍每个工具的 description        │
│  - 选最匹配的那个                      │
│  - 按 parameters 生成参数              │
│  - 输出 tool_call（name + arguments） │
└─────────────────────────────────────┘
  │  tool_call
  ▼
┌─────────────────────────────────────┐
│  4. 执行调用                         │
│  后端调用实际的 API 接口               │
│  （鉴权 + 参数校验 + 发起请求）        │
└─────────────────────────────────────┘
  │  响应结果
  ▼
┌─────────────────────────────────────┐
│  5. 结果处理                         │
│  把接口返回值塞回对话上下文            │
│  大模型根据结果组织语言回答用户        │
└─────────────────────────────────────┘
```

## 配置质量检查清单

发布一个新 CLI 之前，对照检查：

### 基本信息
- [ ] 前缀、分组、动作用英文小写，命名规范
- [ ] 命令标识符合 `{前缀}_cli_{类型}_{分组}_{动作}` 规则
- [ ] 功能描述写清楚了：做什么 + 返回什么 + 适用场景（至少 30 字以上）
- [ ] 命令类型选择正确（API / PAGE）

### 参数配置
- [ ] 所有需要的参数都列了
- [ ] 必填参数标记正确（能有默认值的就不要设必填）
- [ ] 每个参数的描述都写了，不是空的
- [ ] 有枚举值的参数都写清楚了取值范围
- [ ] Array 类型的参数配置了 itemType
- [ ] 参数顺序合理，重要的在前

### API 配置（API 型）
- [ ] URL 和 method 正确
- [ ] 鉴权类型选对了
- [ ] 请求 Schema 完整：类型、必填、枚举、默认值、描述
- [ ] 响应 Schema 能覆盖主要返回字段
- [ ] 工具描述简要说明了接口用途

### 召回标签
- [ ] 至少配置了 DOMAIN 标签（业务域）
- [ ] 配置了 2-3 个 ALIAS 标签（用户常见说法）
- [ ] 配置了 OP 标签（操作动词）
- [ ] 权重设置合理：DOMAIN > ALIAS > OP > SLOT
- [ ] 匹配模式选对了（别名一般用 contains，编码用 exact）

## 常见问题

**Q：命令名改了有什么影响？**
A：命令名是全局唯一标识。如果改了，所有挂载了这个 CLI 的项目的缓存和向量索引都要重建。建议尽量不要改。

**Q：参数命名用驼峰还是下划线？**
A：统一用驼峰（camelCase），和后端接口的 JSON 字段保持一致，减少映射成本。

**Q：描述越长越好吗？**
A：不是。准确、清晰最重要。大概 50-200 字比较合适——太短说不清楚，太长浪费 token，大模型也懒得看。

**Q：召回标签越多越好吗？**
A：不是。5-10 个高质量标签比 30 个低质量标签效果好。重点是 DOMAIN 和高质量 ALIAS。
